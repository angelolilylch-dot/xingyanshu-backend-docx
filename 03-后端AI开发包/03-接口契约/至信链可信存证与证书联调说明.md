# 至信链可信存证与证书联调说明

## 已实现范围

后端 Provider 为 `zxchain`，使用仓库内 `nft_wallet_sdk` 的 `GenerateApiSign` 和 `SignByPriKey` 完成厂商要求的接口签名。业务链路为：

```text
业务快照 SHA-256
  -> POST /api/v1/ev/save
  -> GET /api/v1/ev/query
  -> POST /api/v1/ev/cert
  -> GET /api/v1/ev/cert（轮询至 certUrl）
```

`evId` 保存到 `evidence_record.receipt_no`，交易号保存到 `chain_transaction_hash`，区块高度保存到 `chain_block_height`。迁移 `000054_add_evidence_certificate.sql` 新增 `evidence_certificate`，状态为 `PENDING_REQUEST`、`PENDING`、`READY`、`FAILED`；它与平台生成的授权凭证 PDF 表 `auth_certificate` 完全不同。

Worker 每轮处理成功但尚未建证书任务的存证记录：先查询链上存证，再请求生成证书，随后轮询至证书地址可用。失败采用最多五次、递增分钟的补偿；不会把失败或无回执记录推进为成功。

## 接口清单与边界

以下均为后端 `ZXChainProvider` 到至信链的服务端调用，不是星衍树的 `/api/v1` 对外 API，浏览器和前端不得直接调用。

| 厂商方法 | 厂商路径 | 本系统动作 | 关键结果 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/ev/save` | 提交业务快照 SHA-256 | `evId`、`txId`、区块高度 |
| `GET` | `/api/v1/ev/query?evId=...` | 确认已保存的存证 | 存证状态和链上结果 |
| `POST` | `/api/v1/ev/cert` | 对已确认的 `evId` 申请生成证书 | 厂商证书任务状态 |
| `GET` | `/api/v1/ev/cert?evId=...` | 异步轮询证书 | `certUrl` 和厂商状态 |

厂商认证头 `Secret-Id`、`Signature-Time`、`Signature`、`Nonce`、`Cloud-trace-id` 以及业务签名均由 Provider 和私有运行环境完成；它们、私钥和签名原文不得进入数据库、日志、接口响应或前端包。

`certUrl` 会持久化到 `evidence_certificate.certificate_url`。未来需要在前端展示时，必须通过星衍树新增的受权限保护的“业务对象证书查询”接口按对象和数据范围返回；不得把厂商 URL、`evId` 或任何认证材料拼成匿名公共接口。当前尚未注册此平台查询接口，因此前端只能展示既有业务存证状态，不能直接取得 `certUrl`。

## 部署配置

私有部署配置可写为以下环境变量引用，任何实际值都不得提交到 YAML、日志或前端：

```yaml
evidence:
  provider: ${XINGYANSHU_EVIDENCE_PROVIDER} # zxchain
  endpoint: ${XINGYANSHU_EVIDENCE_ENDPOINT} # https://open.zxchain.qq.com
  secret_id: ${XINGYANSHU_EVIDENCE_SECRET_ID}
  secret_key: ${XINGYANSHU_EVIDENCE_SECRET_KEY}
  public_key: ${XINGYANSHU_EVIDENCE_PUBLIC_KEY}
  private_key: ${XINGYANSHU_EVIDENCE_PRIVATE_KEY}
  timeout: ${XINGYANSHU_EVIDENCE_TIMEOUT} # 例如 10s
```

为兼容部署环境，也支持对应的 `ZXC_EVIDENCE_*` 变量（包括 `ZXC_EVIDENCE_TIMEOUT`）。现有 `config/test.yaml` 仍保留 `mock`，仅在显式设置 `XINGYANSHU_EVIDENCE_PROVIDER=zxchain` 时覆盖为真实 Provider。

## 验收顺序

1. 用 `xingyanshu migrate -config <私有配置>` 应用 `000054`。
2. 启动 server 和 worker；创建一条会产生存证的业务对象。
3. 核验 `evidence_record` 的 `receipt_no`、`chain_transaction_hash`、`chain_block_height`。
4. 等待 Worker 将 `evidence_certificate` 推进到 `READY`，并核验其 `certificate_url`。证书 URL 只能通过后续受权限保护的后端查询接口提供，不能直接下发私钥或签名材料。

## 测试边界

`internal/platform/evidence/zxchain_test.go` 以本地 HTTP 服务验证四个端点、签名头和返回映射；日常单测不调用真实至信链。`TestZXChainLiveIntegration` 仅在设置 `XINGYANSHU_RUN_ZXCHAIN_TESTS=1` 时访问真实租户；它使用固定非业务 Hash，验证私钥签名与公钥配对、存证提交/查询、证书申请/查询。2026-11-06 已通过一次真实租户联调。证书生成是异步的，正式 Worker 继续轮询直至 `READY` 和 `certificate_url` 可用。
